# Learned sibling ranker: instances, split and replication

Experiments of the learned GNN heuristic (`-u GNN --ranker_model`). The code
is the package `lib/gnn_epddl` (see its README); this folder holds what the
experiments were run on.

The benchmark problems are test problems only. Training and validation use
generated instances (`instances/`), written by the package's generators
from templates of the benchmark problems, with the benchmark domain files
unchanged.

## Contents

| Path | What |
|---|---|
| `instances/<tier>/act_lib.epddl` | the tier's action library (the benchmark's) |
| `instances/<tier>/<family>/domain.epddl` | the benchmark domain file |
| `instances/<tier>/<family>/problems/*.epddl` | the generated problems (174) |
| `split.csv` | training and validation instances per family (columns family, tier, problem, label, reason = sub-family) |
| `scripts/` | the replication steps, in order |
| `models/` | the exported models (see `models/README.md`) |

Generated problems per family: active-muddy-child 18, blocks-world 50
(classical 24, epistemic 14, clumsy 12), cloud-scheduling 25,
consecutive-numbers 12, gossip 38, search-and-rescue 21,
selective-communication 10. `split.csv` uses 3 training and 2 validation
instances per sub-family (one validation instance for gossip imp-deceived),
69 rows in all; the other generated problems were candidates (smaller or
larger variants, or problems not chosen by the split rule below).

How the split was chosen (per sub-family; cloud-scheduling: see below): training = the smallest, the
middle and the largest instance (by the number of states in its training set)
among the instances whose search tree was generated; validation = the two
largest instances by BFS plan length, then BFS nodes, among the instances that
passed the check, have a plan of length at least 3, have no training set and
were not set aside as unused.

cloud-scheduling: training g-cloud-17/18/19 (fresh task first, 2 tasks, 2
tenants) and validation g-cloud-22/23 (fresh-first 3-task shapes). These rows
replaced a first choice (training g-cloud-02/04/06, validation g-cloud-07/09)
on which the per-domain cloud-scheduling model solved neither validation
problem at any checkpoint; `split.csv` is the only split. Models whose
families do not include cloud-scheduling -- the no-physical transfer model
(gossip, selective-communication, active-muddy-child, consecutive-numbers) and
the sub-family models (blocks-world and gossip) -- train and validate on the
same rows under either choice.

## Replication

From the repository root, after building deep with ONNX support
(`./build.sh nn`) and installing `lib/gnn_epddl/requirements.txt`:

```
./exp/gnn_epddl/scripts/1_generate.sh     # problems (byte-identical to instances/)
PLANK=<plank> BENCHMARKS=<benchmark root> ./exp/gnn_epddl/scripts/2_check.sh
./exp/gnn_epddl/scripts/3_data.sh         # search trees and training sets of split.csv's training instances
./exp/gnn_epddl/scripts/4_train.sh        # per-domain (seeds 0-2), general and subset runs
./exp/gnn_epddl/scripts/5_select.sh       # checkpoint per run
./exp/gnn_epddl/scripts/6_export.sh       # models/cpu (fast export) and models/gpu (standard export)
RUNNER=<iepc2026-runner checkout> ./exp/gnn_epddl/scripts/7_run.sh   # the planner runs on the 100 benchmark problems
```

Settings are in `scripts/env.sh` (deep binary, training device, work folder
`work/`, which holds data, checkpoints and logs and is not versioned).
Training ran on a GPU (`DEVICE=cuda`); validation searches always run on the
CPU. A tree is generated by BFS when BFS fits the limits (12 GiB, 600 s) and
by DFS otherwise, so a machine with other limits can produce a different tree
for the largest instances.

Test runs on the benchmark problems use the exported models:

```
deep <domain> <problem> --act_lib <lib> -b -c --fast-comparison -s HFS -u GNN --onnx_threads 1 \
     --ranker_model exp/gnn_epddl/models/cpu
```

Step 7 runs every configuration of the experiments through the competition
runner (600 s CPU, 16 GiB, 30 jobs): `bfs`, `hfs-cpu` (per-domain rankers,
CPU), `hfs-cpu-gpu` (states with at least 10000 edges on the GPU; needs deep
built with `./build.sh nn use_gpu` (add `force_gpu` when the CUDA 12 runtime
is not installed system-wide, e.g. only as Python packages), which also runs
every CPU-only configuration, and the CUDA 12 and cuDNN 9 libraries on
`LD_LIBRARY_PATH`, and runs 6 jobs with 6000 MiB of GPU memory each), the one-model
configurations `general`, `subset`, `no-spreading`, `no-puzzle`,
`no-physical`, the beam searches `beam8`, `beam16`, and the untrained network
`untrained` (a control). Pass configuration
names to run a subset. CPU times are comparable across configurations only on
the CPU-only ones: time spent on the GPU is not CPU time.
